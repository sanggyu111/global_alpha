# 01. 기획 — STAYPOINT 호텔 예약 서비스

> 출처: ZIVO 채용 사전 과제 문서 (2.1 ~ 부록 B)
> 이 문서는 **무엇을, 어디까지, 어떤 규칙으로** 만들지 정한다. **어떻게**(테이블, API, 락 방식, 기술)는 `02-design.md` 에서 정한다.

---

## 1. 목표

가상의 호텔 예약 서비스 STAYPOINT 의 핵심 흐름 하나를 **끝에서 끝까지, 신뢰할 수 있게** 구현한다.

```
객실 검색 → 예약 생성(PENDING · 재고 선점) → 결제(모의 PG) → 예약 확정(CONFIRMED) → 취소 · 환불(CANCELED)
```

### 이 과제에서 증명해야 하는 것

1. **동시에 두 사람이 마지막 객실을 예약해도 초과예약이 생기지 않는다.** (과제의 핵심)
2. **결제와 예약은 어긋나지 않는다.** 중복 통지·연타·타임아웃이 와도 한 번만 처리되고, 결제만 남는 상태는 보상되거나 운영자에게 드러난다.
3. **모든 기술 선택과 설계 판단에 이유가 있고, 지원자가 직접 설명할 수 있다.**

### 성공 기준

| 기준 | 측정 방법 |
|---|---|
| 초과예약 0건 | 재고 K 에 N(>K) 동시 요청 → 성공 정확히 K 건 (테스트 실행 결과 README 첨부) |
| 중복 처리 0건 | 같은 승인 통지 2회 이상 → 결제 1건, 상태 전이 1회 (테스트) |
| 환불 금액 정확 | 정책 구간 경계값 테스트 통과 |
| 재현 가능 | 깨끗한 환경에서 README 커맨드만으로 실행 |
| 접속 가능 | 배포 URL (무료 티어) |
| 설명 가능 | README 8개 질문에 모두 답함 |

## 3. 사용자와 범위

### 액터

| 액터 | 식별 | 하는 일 |
|---|---|---|
| 게스트 (사용자) | 헤더 `X-User-Id` | 검색, 예약, 결제, 취소, 내 예약 조회 |
| 관리자 | 헤더 `X-User-Id` + 관리자 경로 (인증 없음) | 예약 목록 조회, 재고·요금 등록/수정 |
| 모의 PG | 내부 HTTP 엔드포인트 | 승인/취소 처리, 승인 결과 통지(콜백) |
| 시스템 스케줄러 | — | 선점 만료 해제, 결제 취소 재시도 |

### 범위

| 포함 (In) | 제외 (Out) — 이유 |
|---|---|
| 필수 요구사항 6개 전체 | 회원가입·로그인 — 과제에서 평가 대상 아님 명시 |
| 모의 PG (지연·실패율 조절) | 실제 PG 연동 — 과제에서 불필요 명시 |
| 선점 만료 처리 | 예약 변경(날짜·인원 수정) — 요구사항 아님 |
| 결제 취소 재시도 + 운영자 확인 대상 분류 | `COMPLETED` 자동 전이(체크아웃 후) — 흐름의 핵심 아님. 상태만 정의 |
| 로컬 재현 환경 + 무료 티어 배포 | 이메일/알림 발송, UI 디자인 |
| | 가산점 항목 — 필수 완료 후 시간이 남을 때만 (8장) |

## 4. 기능 요구사항 (FR)

우선순위는 과제 FAQ 기준: **R2 예약 → R3 결제 → R5 취소/환불 → R1 조회 → R6 화면 → R4 재시도**.
시간이 부족하면 뒤에서부터 포기하고 README 에 명시한다.

### P1. 예약 생성 · 재고 선점 (과제 R2)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-RES-1 | 객실 타입·체크인·체크아웃·인원·예약자 정보(이름, 연락처)로 예약을 만든다 | 생성 시 상태 `PENDING`, 예약번호 발급, 총액 확정 저장 |
| FR-RES-2 | 예약 생성과 동시에 숙박 기간 **모든 날짜**의 재고를 1실씩 선점한다 | 한 날짜라도 재고가 없으면 예약 전체 실패, 일부 날짜만 차감되는 일 없음 |
| FR-RES-3 | **어떤 동시 요청 상황에서도 재고를 초과하는 예약은 생성되지 않는다** | 재고 K 에 N 동시 요청 → 정확히 K 건 성공, 나머지는 "재고 없음" 응답 |
| FR-RES-4 | 선점에는 만료 시간이 있다 (기본 **10분**, 설정값) | 만료 시각 경과 + 미결제 예약은 재고가 복원되고 종료 상태가 된다 |
| FR-RES-5 | 입력 검증 | 체크인 < 체크아웃, 체크인 ≥ 오늘, 숙박 1~30박, 인원 1 ≤ n ≤ 객실 정원 위반 시 거부 |
| FR-RES-6 | 같은 예약 요청 재전송(연타)이 예약을 여러 개 만들지 않는다 | 같은 멱등 키 재요청 → 기존 예약 반환 |

### P2. 결제 · 확정 (과제 R3)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-PAY-1 | 모의 PG 승인 API: 금액·주문번호 → `approved` / `failed` | 외부 PG 가입 없이 동작 |
| FR-PAY-2 | 모의 PG 의 **지연과 실패율을 조절**할 수 있다 | 쿼리 파라미터 또는 설정값으로 실패율(0~100%)·지연(ms) 지정 |
| FR-PAY-3 | 모의 PG 취소 API: 승인된 결제를 전액/부분 취소 | 취소 금액 ≤ 잔여 승인 금액, 초과 시 거부 |
| FR-PAY-4 | 결제 승인 성공 시 예약을 `CONFIRMED` 로 전이 | 승인 1건 ↔ 확정 1건 |
| FR-PAY-5 | **승인 결과 통지가 2번 이상 와도 중복 처리되지 않는다** | 결제 레코드 1건, 상태 전이 이력 1건, 응답은 동일 |
| FR-PAY-6 | 결제 버튼 연타·타임아웃 후 재시도가 이중 결제를 만들지 않는다 | 같은 예약에 승인된 결제는 최대 1건 |
| FR-PAY-7 | **결제는 승인됐는데 확정이 실패하면 결제가 그대로 남지 않는다** | 보상 취소 요청 생성 → 실패 시 재시도(P6) → 최종 실패 시 운영자 확인 대상 |
| FR-PAY-8 | 선점 만료 후 도착한 승인은 확정하지 않는다 | 승인 결과는 보상 취소 대상으로 처리, 예약은 확정되지 않음 |
| FR-PAY-9 | 예약 금액과 결제 금액이 다르면 확정하지 않는다 | 금액 불일치 → 보상 취소 + 기록 |

### P3. 예약 취소 · 환불 (과제 R5)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-CAN-1 | 취소 시점에 따라 환불 금액을 계산한다 (정책 5장) | 경계값 테스트 통과 |
| FR-CAN-2 | 취소 시 숙박 기간 모든 날짜의 재고를 복원한다 | 취소 전후 `잔여 재고` 가 정확히 1씩 증가 |
| FR-CAN-3 | 상태를 `CANCELED` 로 전이하고 이력을 남긴다 | 이력에 사유·주체·시각 기록 |
| FR-CAN-4 | 확정 예약 취소 시 환불 금액만큼 PG 취소를 요청한다 (환불 0원이면 PG 호출 없음) | 부분 취소 금액 = 환불 금액 |
| FR-CAN-5 | `PENDING`(미결제) 예약 취소 시 결제 없이 재고만 복원 | 환불 0원, PG 호출 없음 |
| FR-CAN-6 | **이미 `CANCELED` 인 예약을 다시 취소하면** 정책 5.3 대로 동작 | 재고·환불이 두 번 처리되지 않음 |
| FR-CAN-7 | 본인 예약만 취소할 수 있다 | 다른 `X-User-Id` → 거부 |

### P4. 숙소 / 객실 조회 (과제 R1)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-SRCH-1 | 숙소 목록과 상세, 숙소의 객실 타입 목록 | — |
| FR-SRCH-2 | 체크인·체크아웃·인원으로 **예약 가능한 객실만** 조회 | 숙박 기간 **모든 날짜**에 잔여 재고 ≥ 1 이고 요금이 등록되어 있고 정원 ≥ 인원인 객실 타입만 노출 |
| FR-SRCH-3 | 1박 요금과 총 숙박 요금 표시 | 날짜별 요금 목록 + 합계. 총액 = 각 날짜 요금의 합 |
| FR-SRCH-4 | 날짜별로 요금이 다를 수 있다 (주말·성수기) | 요금은 객실 타입 × 날짜 단위로 저장 |

### P5. 조회 화면 (과제 R6)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-UI-1 | 검색 → 객실 선택 → 예약 정보 입력 → 결제 → 결과 화면 | 핵심 흐름을 브라우저에서 끝까지 수행 가능 |
| FR-UI-2 | 사용자: 내 예약 목록 + 상세 (상태, 결제 금액, **환불 예정 금액**) | 상세에서 "지금 취소하면 얼마 환불" 표시, 취소 버튼 |
| FR-UI-3 | 관리자: 예약 목록 — 상태·날짜·숙소 필터, 페이지네이션 | 필터 조합 + 페이지 이동 |
| FR-UI-4 | 관리자: 객실 타입별 날짜 재고·요금 등록/수정 (기간 일괄 지정) | 이미 예약된 수보다 재고를 줄이면 거부 |
| FR-UI-5 | 관리자: 운영자 확인 대상(취소 최종 실패 등) 목록 | 재시도 소진 건 확인 가능 |
| FR-UI-6 | UI 는 기본 HTML 수준. **서버/클라이언트 경계와 캐싱 설계가 핵심** | 설계 문서와 README Q5 에 근거 기록 |

### P6. 결제 취소 재시도 (과제 R4)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-RTY-1 | PG 취소 실패(타임아웃, 5xx)는 재시도 대상으로 저장한다 | 취소 요청이 유실되지 않음 |
| FR-RTY-2 | 재시도는 간격을 두고 자동 수행된다 (기본 최대 **5회**, 점증 간격) | 시도 횟수·마지막 오류·다음 시도 시각 기록 |
| FR-RTY-3 | **무한 재시도 금지.** 최대 횟수 초과 시 운영자 확인 대상으로 분류 | 상태가 "수동 처리 필요" 로 바뀌고 관리자 화면에 노출 |
| FR-RTY-4 | 재시도로 인해 같은 취소가 두 번 실행되지 않는다 | PG 취소도 멱등 키로 보호 |

## 5. 비즈니스 정책

> **[결정]** 표시는 과제가 정의를 위임한 항목에 대한 이번 기획의 결정이다. README 에도 그대로 옮긴다.

### 5.1 숙박일과 재고 단위

- 숙박일(`stay_date`)은 **체크인 날짜 ~ 체크아웃 전날**. 체크아웃 날짜는 재고를 쓰지 않는다. (1박 2일 = 1일치 재고)
- **[결정]** 예약 1건 = 객실 1실. 여러 실이 필요하면 예약을 여러 건 만든다. → 동시성 문제를 "날짜별 1실 차감" 으로 단순화
- 재고는 **객실 타입 × 날짜** 단위로 관리한다 (개별 호수 배정 없음).

### 5.2 환불 정책

기준: **체크인 날짜까지 남은 일수** `D = 체크인 날짜 − 취소 날짜` (날짜 단위, **Asia/Seoul** 기준)

| 남은 일수 D | 환불율 | 예 (체크인 10/20) |
|---|---|---|
| D ≥ 7 | 100% | ~ 10/13 |
| 3 ≤ D < 7 | 70% | 10/14 ~ 10/17 |
| 1 ≤ D < 3 | 50% | 10/18 ~ 10/19 |
| D ≤ 0 (당일·노쇼·체크인 이후) | 0% | 10/20 이후 |

- **[결정]** "7일 전까지" 를 "D ≥ 7" 로 해석. 경계값(D=7, 6, 3, 2, 1, 0)을 테스트로 고정한다.
- 환불 금액 = 결제 금액 × 환불율, **원 단위 내림** (고객에게 과다 환불하지 않음). 통화는 KRW 고정.
- 정책 표는 코드 한 곳에 상수로 둔다.

### 5.3 상태와 취소 규칙

```
PENDING ──결제 승인──▶ CONFIRMED ──(체크아웃 후)──▶ COMPLETED
   │                      │
   ├─사용자 취소──▶ CANCELED ◀──사용자 취소──┘
   └─선점 만료──▶ (종료 상태: 설계에서 CANCELED(사유 EXPIRED) 또는 EXPIRED 로 확정)
```

- **[결정] 이미 `CANCELED` 인 예약을 다시 취소** → **멱등 성공**으로 처리한다. 상태·재고·환불은 변경하지 않고 **최초 취소 결과(환불 금액 등)를 그대로 반환**한다.
  - 이유: 네트워크 재시도나 버튼 연타로 같은 취소가 다시 와도 클라이언트가 실패로 오해하지 않게 하고, 중복 환불 가능성을 원천 차단.
  - `COMPLETED` 예약 취소는 거부한다.
- 선점이 만료된 `PENDING` 예약은 결제할 수 없다 (결제 요청 시 거부).

### 5.4 결제 규칙

- 예약 1건에 **승인된 결제는 최대 1건**.
- 결제 금액은 예약 생성 시 확정한 총액과 같아야 한다 (요금이 이후에 바뀌어도 예약 금액은 고정).
- 결제 실패(`failed`)는 예약을 즉시 취소하지 않는다. 선점 만료 전까지 재결제 가능.

### 5.5 관리자 재고·요금 규칙

- 재고 총량은 **이미 예약된 수 미만으로 줄일 수 없다**.
- 요금 변경은 **이미 생성된 예약 금액에 영향을 주지 않는다**.

## 6. 비기능 요구사항 (NFR)

| ID | 분류 | 요구사항 |
|---|---|---|
| NFR-1 | 정합성 | 재고 초과 방지는 애플리케이션 검사만이 아니라 **DB 수준에서도 보장**된다 |
| NFR-2 | 정합성 | 외부(PG) 호출은 DB 트랜잭션 밖에서 수행해 락·커넥션을 장시간 점유하지 않는다 |
| NFR-3 | 멱등성 | 예약 생성, 결제 요청, 승인 통지, 취소, PG 취소에 각각 멱등 키가 정의된다 |
| NFR-4 | 추적성 | 예약 상태 전이와 결제·취소 시도가 모두 이력으로 남는다 |
| NFR-5 | 운영 | 정합성이 깨질 수 있는 지점(보상 실패, 재고 불일치)은 운영자가 조회할 수 있다 |
| NFR-6 | 테스트 | 동시성 테스트는 운영과 같은 DB 엔진(PostgreSQL)에서 실행한다 |
| NFR-7 | 재현성 | 빈 DB 에서 마이그레이션 + 시드만으로 데모 데이터가 준비된다 |
| NFR-8 | 보안 | 시크릿은 환경변수로만 주입하고 저장소에 커밋하지 않는다 |
| NFR-9 | 배포 | 프론트·백엔드·DB 모두 무료 티어. 과금 선택 금지 |
| NFR-10 | 설정 | 선점 만료 시간, PG 실패율/지연, 재시도 횟수/간격은 설정으로 바꿀 수 있다 |
